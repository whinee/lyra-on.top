# Master Prompt #4 — Pre-Push Security Audit & Authorized GitHub Push

## Mission

Safely publish the intended WhiskerFrame / `lyra-on.top` repository changes to GitHub **only after a real secrets-and-privacy review and project checks pass**. The user explicitly authorizes pushing after those gates. This overrides earlier “do not push without approval” instructions for this bounded task only.

**This is not deployment authorization.** Do not merge into a deployment-triggering branch, deploy a Worker, alter DNS/routes/custom domains, or perform production cutover. If pushing a branch would trigger production deployment, push a review/feature branch instead.

## Before editing or pushing

1. Resolve the actual repository root, branch, remotes, upstream, working-tree and index state; fetch remote refs and determine exactly which commits/files would be published. Read `AGENTS.md`, `docs/ai/STATE.md`, current handoff, `.agents/rules/`, and the documented Git/GitHub workflow skill. Read applicable `docs/dev/ai/master-prompts/1.md`–`3.md` if present.
2. Inspect all workflow triggers—especially `.github/workflows/deploy-worker.yml` and any legacy VPN/SSH deploy workflow—before choosing the push target. Never let this push accidentally trigger production deployment.
3. Preserve all user and other-agent work. Never use `reset --hard`, force-push, delete worktrees, discard changes, or rewrite shared history.

## Mandatory security and privacy gate

Scan the **entire current repository**, every tracked file, all staged/unstaged changes, ignored-but-relevant files that could accidentally be added, and the Git history/commits that would be published. Use a maintained secret scanner such as Gitleaks or TruffleHog where available, plus manual targeted review; confirm scanner scope and exit status. Do not rely on `.gitignore` or filename checks alone.

Check for at least:

- Cloudflare/GitHub/API tokens, passwords, session cookies, private keys, certificates, signing material, database credentials, webhook secrets, `.env` values, and hard-coded credentials.
- PII or unintended personal data: private email/address/phone details, personal documents, local usernames or absolute paths, private/internal hostnames or IPs, logs, browser profiles, data exports, screenshots, backups, and metadata.
- `.env`, credential files, generated artifacts, caches, virtual environments, local databases, and large or unrelated files accidentally staged or tracked.
- Git history: a secret removed from the latest tree is still a blocker if it remains in commits being pushed.
- Workflow supply-chain hazards, excessive permissions, unpinned or suspicious actions, shell injection from untrusted event data, and accidental production triggers.

Never echo, paste, or include detected secret values in terminal summaries, test logs, commits, prompts, or final reports. Report only redacted snippets/fingerprints, file paths, finding type, severity, and remediation status.

The user previously specified `lyraphasma@gmail.com` as the website contact email. Treat it as intentionally public **only in the intended public contact locations**; do not mistake that one approved address for a credential. Flag unexpected occurrences or other personal data for review.

### Finding handling

- Fix clear, local, low-risk issues safely: exclude local secret files, correct `.gitignore`, replace accidentally added example credentials with unmistakable placeholders, and unstage irrelevant artifacts without deleting the user's local data.
- Re-scan after fixes, then inspect the complete staged diff and verify no secret can be reached through the commits being pushed.
- **BLOCK the push** if an active/credible secret or sensitive personal data remains, a scanner reports unresolved high-confidence findings, scan coverage is materially incomplete, or a leaked secret remains in publishable history. Do not silently rewrite history or rotate credentials. Explain the redacted finding and ask for the specific approval/action needed. Recommend immediate credential rotation when a real credential may have been exposed, without exposing it.
- Distinguish confirmed findings from false positives and document the evidence for any suppression. Do not add broad allowlists merely to get a green scan.

## Validation and publication

1. Run `git diff --check`, the repository's documented quality gate (including `just check`), and applicable tests/build/config validation for the Cloudflare Workers workflow. Fix failures and rerun affected checks. Do not claim an unrun check passed.
2. Inspect the exact commits and staged diff. Stage and commit only the intended deployment-pipeline/runbook/state changes plus other clearly in-scope work approved by the user. Do not include `.env`, credentials, unrelated changes, local artifacts, or temporary reports.
3. Confirm the push destination is the expected `whinee/lyra-on.top` remote (or report any mismatch), confirm credentials and upstream, and ensure the destination branch cannot deploy production as a side effect. If the current branch triggers production deployment, create/push a review branch and stop before merge.
4. Push normally to the verified branch. **No force-push and no deployment.** If there are no new changes/commits to push, report that fact rather than manufacturing a commit.
5. Verify the remote contains the pushed commit(s) and that the push succeeded. Update `docs/ai/STATE.md` or the prescribed append-only handoff only if this is consistent with project rules; include the audit tools/versions, commands, outcomes, branch, commit SHA, remote, and remaining caveats without leaking findings.

## Completion report

Provide:

- Repository, remote, branch, commit SHA(s), and whether the push was verified.
- Exact security-scanning commands/tools and versions, files/history scanned, exit statuses, and findings summary (redacted).
- `just check` and relevant test/build results, including failures or unrun checks.
- Whether the selected branch can trigger deployment and why production was not deployed.
- Any blocked actions, remediation still required, or credential-rotation/history-cleanup advice.

Do not report success based only on a planned scan, a clean working tree, or a successful local commit. The mission is complete only when the security gate passes and the intended commits are confirmed on the remote review branch.
