# Master Prompt #6 — Diagnose the Latest GitHub Commit Failure

## Mission

Independently inspect **GitHub's actual state** for `whinee/lyra-on.top`, identify the real error associated with the latest relevant commit/check/deployment, and fix it where safe. Do not rely solely on local test output, prior summaries, or assumptions. This is an execution task, not a plan-only request.

## 1. Start from GitHub, not assumptions

- Confirm repository identity and authentication, then query the live remote default branch and latest commit SHA. Inspect the commit's check suites, check runs, PR status, and associated GitHub Actions workflow runs directly through `gh`/GitHub API or the authenticated GitHub interface.
- Find the exact failed, cancelled, timed-out, skipped, or unexpectedly absent check. Open the full logs and annotations for the relevant job/step; capture the workflow name, run ID/URL, commit SHA, failing command, error message, and useful preceding context.
- Inspect the latest Cloudflare Worker deployment workflow too. Distinguish a code/CI failure from a GitHub Actions permission or secret problem, build/configuration failure, and a successful deployment followed by a runtime/HTTP problem.
- If the latest commit has no failing checks, do not invent an error. Inspect the latest relevant workflow/deployment runs and report what GitHub actually shows, including whether checks never triggered or are still pending. Use bounded polling for in-progress runs.
- Verify the actual latest remote SHA before making changes. Do not trust a stale local branch or an earlier handoff as current state.

## 2. Diagnose and repair

- Read `AGENTS.md`, `docs/ai/STATE.md`, the latest handoff, `.agents/rules/`, and relevant test, build, and deployment instructions before editing.
- Reproduce the specific failure locally where feasible. Trace it to root cause; do not merely suppress the error, weaken a test, skip a required job, broaden permissions, or relabel a failure as passing.
- Preserve all user/agent work. Inspect working-tree changes before editing. Never run destructive cleanup, `git reset --hard`, force-push, or rewrite shared history.
- Make the smallest correct fix. Add or update regression coverage when appropriate, then run the failing command/job's equivalent plus the relevant project gates (`just check`, `just lighthouse`, `just screenshots`) when applicable. Read generated Lighthouse reports and screenshots rather than treating command exit status alone as proof.
- For GitHub-specific issues, check workflow YAML, trigger conditions, permissions, secrets *by presence/name only*, artifact paths, build output paths, environment protection, and Cloudflare/Wrangler configuration. Never print, copy into logs, or commit secret values. Do not ask the user to paste tokens into chat.

## 3. Commit, push, and verify safely

- If a focused, verified fix is appropriate, commit it on the appropriate branch and use the repository's normal PR/branch-protection process. Do not push directly to protected `main` if repository rules require a PR. Do not merge unrelated changes.
- Before pushing, inspect the exact diff and staged files for credentials, unintended PII, local artifacts, and accidental secrets; run the repository's secret scanner (Gitleaks if installed) over the intended commit range. Stop and explain any credible unresolved secret finding; never expose the value.
- Push only the intended fix using a normal, non-force push. Then query GitHub again and verify the pushed SHA, latest check-run conclusions, and relevant Actions/deployment run. Inspect new failure logs and continue fixing only where safe; do not declare success while required checks are failing or still unverified.
- Do not change DNS/custom-domain routes, rotate credentials, modify unrelated VPN/SSH infrastructure, disable protections, or bypass mandatory approval. A normal Worker deployment already configured to run from the production branch is in scope only if the reviewed repository workflow and existing authorization permit it.

## 4. Durable state and evidence-based report

Update `docs/ai/STATE.md` or the prescribed handoff journal if project rules require it. Record the remote commit SHA, workflow/run URL and ID, failed job/step, root cause, changed files, exact commands/results, secret-scan scope, fix commit/PR, and final GitHub check/deployment state. Do not record credentials or sensitive log contents.

Report concise evidence: repository/default branch; SHA examined; GitHub check and workflow links/statuses; exact root cause (or state clearly that no failure was visible); minimal fix; tests and scanner results; pushed SHA/PR if applicable; deployment result; and remaining blockers. Never invent log output, claim a run passed without checking GitHub, or stop at a speculative diagnosis.
