# Master Prompt #3 — Cloudflare Workers Deployment via GitHub Actions

## Mission

Implement and document a secure, repeatable GitHub Actions deployment for `lyra-on.top` to **Cloudflare Workers**, with a clear operator checklist of every external prerequisite. This is an execution task: modify the repository, validate the pipeline as far as credentials allow, and leave no ambiguity about what Lyra must configure next. Do not ask Lyra to paste secrets into chat.

## Read state first

Read `AGENTS.md`, `docs/ai/master-context.md`, `docs/CONTRACT.md`, `docs/RECON.md`, `STATE.md`, `docs/ai/STATE.md`, `docs/ai/DEPLOY.md`, `docs/ai/WORKER.md`, `docs/ai/orchestrator-prompt.md`, the root and `worker/` Wrangler configs, `justfile`, and every active workflow. Verify the real repo root, branch, worktree, and uncommitted changes. Follow current repo rules and the documented Orca workflow; fan out only independent tasks with explicit file ownership. Treat this prompt as the user's explicit request to target Workers, even if older docs describe Pages, but reconcile the architecture before changing anything.

## Architecture and safety

- The current design describes a frozen static site (`just freeze` produces `dist/`) and a separate Python API Worker at `api.lyra-on.top`. Inspect the *current* code and Cloudflare docs; do not assume the API scaffold or any earlier deployment is live.
- Target the primary static site with **Workers Static Assets** using the existing reproducible `dist/` output and Wrangler. Preserve the separate API Worker/config unless evidence shows a necessary change. Never combine the static site and Python API under one Worker or overwrite the API Worker by mistake.
- Root `wrangler.toml` currently reflects Pages-era configuration. Update it to a valid Workers Static Assets configuration only after checking current Wrangler/Cloudflare documentation and the generated site contracts. Verify routing, 404 behavior, `_redirects`, canonical URLs, sitemap, `robots.txt`, and all generated assets.
- Existing production may still be on Pages. Do not create/remove DNS records, detach a Pages custom domain, change zone settings, or perform the first production route cutover without explicit operator approval. Prepare the config/workflow and document the precise cutover decision. Use a non-production/`workers.dev` validation path if available, and clearly distinguish that from production success.
- Preserve user changes. No destructive Git commands, no secret values in logs, commits, test fixtures, static output, docs, or artifacts. Do not push, merge, or deploy from the agent session unless the user has explicitly authorized that action. The workflow itself should be ready for the intended automated deploy after the operator enables it.

## Implement

1. Add or revise a dedicated, clearly named workflow under `.github/workflows/` for the primary site Worker. It should validate/build the frozen site first, then deploy with Cloudflare's official `cloudflare/wrangler-action` and Wrangler config. Trigger on pushes to the repository's actual production branch and `workflow_dispatch`; never deploy on pull requests. Add least-privilege `permissions: contents: read`, concurrency protection that avoids overlapping production deployments, a timeout, and sensible path filters only if they cannot skip needed shared changes. Use maintained action versions and follow repository policy for SHA pinning; never use `@master`.
2. Run the real repository gates before deploying (at minimum `just check`; also run/integrate existing Lighthouse and screenshot/audit commands if present and reliable). Ensure the build is deterministic, fails closed on test/build errors, and does not accidentally publish `.env`, source-only/private files, reports, caches, or other non-public content. Retain useful Lighthouse/test reports as GitHub Actions artifacts if practical, without including secrets.
3. Use GitHub repository **Actions secrets** named `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN`. Do not add placeholder token values to files. The deploy job must fail clearly when required credentials are unavailable without printing their values. Do not create unneeded secrets or a personal GitHub token unless repository evidence proves it necessary.
4. Configure a safe preview/staging validation strategy if practical. Document how to run the build and Wrangler dry-run/preview locally, how to inspect a failed action, how to re-run manually, how to verify the live deployment, and how to recover/roll back. Be precise about what Wrangler dry-run can and cannot prove.
5. Audit and reconcile the existing `.github/workflows/deploy.yml` (currently a legacy VPN/SSH workflow in the baseline archive). Do not leave two workflows racing to publish the same target, and do not silently delete an unrelated operational workflow. Explain the evidence and make the safest scoped change; if intent is uncertain, disable neither workflow without operator review.
6. Update the canonical deployment runbook (`docs/ai/DEPLOY.md` and/or the current canonical equivalent), worker docs if needed, and state/task ledger. Clearly separate automated repository changes from dashboard actions Lyra must do.

## Operator handoff — mandatory

In the final report, include a copy/paste checklist with **exact labels, location, purpose, and whether required**:

- `CLOUDFLARE_ACCOUNT_ID`: find in the relevant Cloudflare account dashboard.
- `CLOUDFLARE_API_TOKEN`: create a custom token using Cloudflare's current **Edit Cloudflare Workers** template, scoped only to the intended account and the needed zone/resources. Confirm any extra zone permissions required for the configured custom route from current official docs; request the least privilege that actually works.
- GitHub location: `whinee/lyra-on.top` (verify current repository settings), **Settings → Secrets and variables → Actions → New repository secret**. Store the two values as repository secrets; never commit them, put them in `.env`, or send them to an agent/chat.
- Any required custom-domain/zone prerequisite and the exact action Lyra must take to authorize first production cutover. List `workers.dev` preview separately from `lyra-on.top` production.
- What should happen automatically on a push to the production branch, how to manually trigger deployment, and how to confirm success.

Do not claim the site is live or a deployment passed unless an authenticated deployment and external HTTP checks were actually completed. If credentials/approval are unavailable, complete all local implementation and checks, report the exact remaining human steps, and leave production routing untouched.

## Verification and completion gate

Run the available project gates and validate the workflow syntax/configuration. Inspect actual diffs and build output. Check that all expected public routes/assets exist in `dist/`, no secrets or private files enter the output, and static pages still work without the API Worker. Test the public route only if actually deployed and authorized. Record exact commands, exit statuses, deployment/preview URLs, GitHub workflow status, tested revision, and remaining blockers in the state/handoff docs. Mark unexecuted remote checks `NOT TESTED`, not passed. Do not stop at a plan or YAML file: implement, validate, document, and return the operator checklist.
